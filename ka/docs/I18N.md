# Languages in KrishiAssist (English, Hindi, Hinglish)

One system serves the whole app. This page explains how it works, how to add things, and how to check it.

## The idea in one minute

| What is being shown | Where its wording lives | Who translates it |
|---|---|---|
| Buttons, headings, labels, dropdowns, notices, errors | `frontend/src/i18n/locales/{en,hi,hinglish}.json` | `t('key')` |
| Scheme content (benefits, documents, steps, rules, sources, departments …) | `data/i18n/scheme_text.json` (English text → Hindi / Hinglish) | `useSchemeText()` / `getLocalizedText()` in the browser, `localize_scheme()` on the server |
| Scheme name and description | `translations` block inside each scheme in `data/schemes.json` | same as above |
| Eligibility results | the engine returns a **rule code + parameters**; sentences are in the locale files (`eligibility.rules.*`) | `ruleMessage(criterion)` |
| API errors | the server returns an error **code** (`EMAIL_EXISTS`, `FILE_TOO_LARGE` …); sentences are in `errors.*` | `apiErrorMessage(body)` |
| PDF report, assistant reply | server side: `backend/app/i18n/messages.py` and the scheme catalog | `Accept-Language` / `language` |

There is **one** language state: `frontend/src/i18n/core.ts`. It is saved in `localStorage` (`ka_lang`), every component re-renders when it changes, and the header selector, footer buttons and every page read the same value.

## Frontend

```
frontend/src/i18n/
  core.ts        language state, t(), {{interpolation}}, missing-key tracking
  react.ts       useTranslation(), useLanguage()
  schemeText.ts  scheme catalog, getLocalizedText(), localizeScheme(), useSchemeText()
  format.ts      fieldLabel(), valueLabel(), ruleMessage(), apiErrorMessage(), dateLocale()
  api.ts         apiFetch(): every request goes through it
  locales/       en.json  hi.json  hinglish.json
```

The API mirrors i18next / react-i18next (`t`, `{{name}}`, `returnObjects`, `useTranslation`) and the JSON files are i18next-compatible, so moving to i18next later means replacing `core.ts` internals only. i18next is not a dependency today because it could not be installed when this was built.

Use it like this:

```tsx
const { t } = useTranslation();           // subscribes the component to language changes
<label>{t('fields.land_ownership_type')}</label>
t('matches.rulesMet', { a: 3, b: 5 })     // "3 of 5 rules met" / "5 में से 3 शर्तें पूरी"

const { scheme } = useSchemeText();
const x = scheme(s);                      // x.name, x.benefits, x.documents[].label, x.steps, x.sources ...
getLocalizedText({ en: 'Tractor', hi: 'ट्रैक्टर', hinglish: 'Tractor' })   // or a plain English scheme string
```

Rules for new code: no English in components; no `lang === 'hi' ? … : …`; no second language state. `npm run test:i18n` fails if any of these appear.

### How the app talks to the API

* Scheme data, eligibility results and matches are requested in **canonical form** (English text + codes: `Accept-Language: en`) and translated in the browser. That is why a language switch is instant and a cached result is correct in every language.
* Output the **server renders** (the PDF report) is requested in the selected language (`apiFetch(url, { localized: true })`).
* The API itself localizes whenever asked, for other clients: `GET /api/schemes?lang=hi`, or the `Accept-Language` header. Identifiers (`schemeCode`, `state`, `category`, document `name`, field names, status codes, URLs) are never translated; localized labels are added beside them (`categoryLabel`, `stateLabel`, document `label`).

## Eligibility messages

The engine (`backend/app/engines/eligibility_engine.py`) is unchanged in what it decides. Each criterion result now also has:

```json
{ "ruleCode": "RESIDENCY_MISMATCH", "params": { "field": "state", "expected": "Gujarat", "actual": "Punjab", "requiredState": "Gujarat", "providedState": "Punjab" }, "result": "FAIL" }
```

Codes: `RULE_PASSED`, `RESIDENCY_MATCH`, `RESIDENCY_MISMATCH`, `RULE_FAILED_{EQUALS,NOT_EQUALS,GT,GTE,LT,LTE,IN,NOT_IN}`, `RULE_UNKNOWN`. The old English `explanation` is still sent so existing API callers keep working; the web app no longer displays it. Evaluations saved before codes existed are still rendered, because the code is derived from the stored `field/operator/result`.

To add a code: add it to `backend/app/i18n/rules.py` (`RULE_CODES`, `RULE_TEXT`) **and** to `eligibility.rules.*` in all three locale files. The audit checks the two agree.

## Adding a scheme (or editing one)

1. Add or edit it in `data/schemes.json` in English, including `translations.hi` and `translations.hinglish` for `name` and `description`.
2. Add every new English sentence to `data/i18n/scheme_text.json` under `entries`, with `hi` and `hinglish`.
3. If it uses a new question field, add `fields.<fieldName>` (and `answers.<field>.<value>` for dropdown answers) to the three locale files.
4. Run the checks below. Nothing else needs to change; no component needs touching.

Keep amounts, percentages, units, dates, URLs, acronyms and official names exactly as in the English text.

## Adding a user-facing string

Add the key to `en.json`, `hi.json` **and** `hinglish.json` (same placeholders), then use `t('key')`. Hindi uses the project glossary: लाभ, पात्रता, आवश्यक दस्तावेज़, आवेदन के चरण, अगले कदम, भूमि का स्वामित्व, मुख्य फसल, जिला, आवेदक. Hinglish is Hindi in Roman script with common English terms.

## Missing-translation detection

* Runtime: a missing key (or catalog entry) is **never hidden**. It is logged once (console in development, `logging` warning on the server), recorded (`getMissing()` in the browser, `catalog.missing_report()` on the server), and shown in English; if English is missing too, the key itself is shown. A fallback is not a finished translation.
* Build time:
  * `cd frontend && npm run i18n:audit` : key parity, empty values, `{{placeholder}}` mismatches, Devanagari/Roman script, text identical to English, keys used but undefined, hardcoded English in components, agreement with the backend vocabulary and rule codes, labels for every scheme question field.
  * `cd backend && python -m app.scripts.i18n_audit` : every scheme string has Hindi and Hinglish, amounts / percentages / numbers / acronyms preserved, name and description translated for each scheme, vocabulary and rule texts complete.
  * Add `--write` to either to refresh `docs/translation-audit-report.md`.
  * Text that is *meant* to be identical to English (official names, everyday English UI words in Hinglish) is listed in `frontend/i18n-allowlist.json` and in `data/i18n/scheme_text.json → _meta.keep_as_is`. Those lists are reviewed, not automatic.

## Tests

```
cd frontend && npm run typecheck && npm run check:i18n     # audit + 17 render/behaviour tests
cd backend  && pytest -q ../tests                           # includes test_i18n_core.py and test_i18n_api.py
```

## Known limitations

* **Hindi PDF.** ReportLab does not shape Devanagari (vowel signs and conjuncts print wrongly, e.g. "किसान" → "कसिान"). A Hindi report request is therefore produced in Hinglish and the response says so (`X-Report-Language: hinglish`, `X-Report-Language-Requested: hi`); the app shows a notice. Proper Hindi PDFs need a shaping engine (for example WeasyPrint or `uharfbuzz`).
* **Chat history** keeps the language each assistant reply was written in; replies are not re-translated retroactively.
* **Admin validation messages** (the JSON-schema errors shown when checking a pasted scheme) come from the schema validator and stay in English; the admin screen around them is translated.
